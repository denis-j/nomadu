# App audit, 23 September 2026

A pass over the whole app: every tab, every screen that can be reached, the
sync, the backend and the error paths. Findings are ordered by how much they
cost a real user, not by how interesting they are.

## How it was tested

- **Build**: 1.0.4 (3). Release on the iPhone (`iPhone von Denis`), Debug on the
  simulator (iPhone 17 Pro, iOS 26.5).
- **Driving the app**: Maestro flows with real taps, swipes and scrolls
  (`~/.maestro/bin/maestro`, needs `JAVA_HOME=/opt/homebrew/opt/openjdk@21`).
  Twelve flows, 54 route files, all five tabs and every sub-screen that has a
  route, plus four deliberately broken deep links.
- **Data**: the SQLite databases of both devices read directly (the phone's
  through `devicectl device copy from`), and every Firestore collection of both
  accounts counted against them.
- **Errors**: all 25 unresolved Sentry issues read, the interesting ones traced
  back into the code.
- **Static**: `tsc`, `eslint` over `app lib components hooks contexts constants`,
  and the 64 Cloud Function tests.

## Verdict

The app works. Everything a user does day to day held up under real taps:
tracking, timeline, planning, stays, documents, sharing, visa and tax. The
serious problems were not in the screens but underneath them, in the sync, and
they had been running for two weeks.

| Area | State |
| --- | --- |
| Tracking, timeline, stats | Works. Stats counted wrong, fixed below. |
| Plan, stops, stays, guides | Works. |
| Documents and sharing | Was completely broken in production, fixed. |
| Cloud sync | Was corrupting data daily, fixed. |
| Visa and tax | Works. |
| Error paths | Three screens crashed on a malformed link, fixed. |
| Performance | Slow cold start, see below. Unresolved. |

## Fixed during the audit

### 1. Sync duplicated trips and aborted on every start (critical)

`UNIQUE constraint failed: trips.sync_id`, 135 events in Sentry since 7 September,
context `sync`.

The push writes the cloud document first and stores the new id on the local row
afterwards. The realtime listener gets the document in between, does not
recognise it as this phone's own row, and inserts a **second** local row for it.
The push then tries to claim the id, hits the unique index, throws, and takes the
whole `syncAll` down with it: the last-synced stamp stops moving and the row is
left without an id, so the next start repeats the whole thing with a fresh id.

The damage on the phone: **36 rows for one stay in Berlin**, 594 cloud documents
for 20 live trips, and no successful sync since 18 September.

- `lib/database.ts`: `upsertTripFromCloud` now adopts the local row the document
  belongs to (by `local_id`) instead of inserting a copy, and `setSyncId` gives
  up the id when another row already carries it.
- `lib/userVisas.ts`: same two changes, the visa push had the same shape.
- `lib/sync.ts`: `syncAll` runs every collection even when one fails, and the
  report names the step that broke.

Verified: four launches on the simulator and four on the phone, no new rows, no
rows without a sync id, the stamp moving again, and the Sentry issue silent
since the build went on.

### 2. Document sharing never worked in production (critical)

`storage/unauthorized`, 33 events. The storage rules asked Firestore who was on
the trip (`firestore.get`), and **cross-service rules do not work in this
project**: even a hardcoded path to a document that exists and matches is
refused. Upload and download were both dead, so a shared document had never
once reached another phone.

The audience now sits in the path, so the rules need no Firestore:
`shared/{journey}/{owner}/all/…` and `shared/{journey}/{owner}/u/{uid}/…`
(`storage.rules`, `lib/documentSync.ts`). Both segments are ids only people on
the trip have.

Verified end to end: uploaded from the simulator, the file arrived on the phone
(266 KB, `Documents/documents/…jpg`).

### 3. The tidy-up question came back at every launch (high)

The offer to merge duplicate stops was remembered under the trips' **local row
ids**, which the sync rewrites, so the same question returned on every start. It
is now keyed on the sync ids, and after a cleanup the note is dropped so a later
mess is offered again (`app/(tabs)/(timeline)/index.tsx`). The duplicates that
caused it came from finding 1.

### 4. Stats counted countries twice (medium)

The headline said **22 countries and 50 cities**; the truth is **13 and 41**. The
count was keyed on the country's *name*, and the geocoder used to store whatever
the phone's language was, so "Germany" and "Deutschland" are two rows for one
country. Nine countries are affected. Now counted by country code
(`lib/stats.ts`).

### 5. The tax disclaimer floated over other tabs (medium)

It is a React Native `Modal`, which renders above the whole app. Leaving the tax
screen without dismissing it left it hanging over the timeline and the plans.
Now bound to the screen's focus (`app/(tabs)/(stats)/tax.tsx`).

### 6. Three screens crashed on a malformed link (medium)

`nomady:///(tabs)/(plans)/accommodation`, `…/stop-info` and `…/edit-stop` without
parameters died in `fromYmd`/`parseDate` ("Cannot read property 'split' of
undefined"). The scheme is public, so anything can send those links. They now
show a plain "This stop is no longer here" (`components/MissingRoute.tsx`).

### 7. Location noise reported as failures (low)

`kCLErrorDomain Code=0` ("location unknown") is what iOS says when it cannot get
a fix for a moment: indoors, in a tunnel, right after a start. It is not a
failure, and it accounted for 108 Sentry events in a week. The background task
now ignores exactly that code and still reports every other location error
(`lib/location.ts`).

### 8. Sentry reported "[object Object]" (low)

26 events said nothing at all. Non-Error values are now described by their code
and message (`lib/monitoring.ts`), which is how finding 1 became readable in the
first place.

## Open findings

### A. Cold start is slow (high, not investigated)

Sentry records `launch_duration: 18.0 s` on the phone, three app hangs (2.0–2.8 s,
4.0–4.8 s, one fatal) and **6 watchdog terminations** in five days. In testing the
app needs 15–20 seconds after launch before the first screen is usable.

Two likely contributors, both visible in the code:

- Every pull reads a **whole collection** (`getDocs(collection)`), and a realtime
  `onSnapshot` sits on the trips collection as well. That is 638 documents for
  this account, 594 for the phone, on every single start.
- `getTripsModifiedSince` exists in `lib/database.ts` and nothing calls it: the
  incremental path was intended and never wired up.

Recommendation: pull with `where('updated_at', '>', lastSync)` and keep the full
read for the first sync after a reinstall.

### B. Tombstones are never pruned (medium)

62 % of the trip documents in the cloud are deletion markers (398 of 638 on one
account, 574 of 594 on the other, mostly debris from finding 1). They are read on
every sync and never go away. A scheduled function could drop tombstones older
than, say, 90 days once every client has certainly seen them.

### C. Country names in old rows are localised (medium)

The write path was fixed at some point (`lib/geocoding.ts` canonicalises through
`getCountryName`), but rows written before that still say "Deutschland",
"Kolumbien", "Mexiko". The city screen shows "Berlin / Deutschland" while the
timeline shows "Germany" for the same place. Stats no longer care (finding 4),
but the display is inconsistent.

Recommendation: a one-off pass over `trips` setting `country` from the code.
Cheap, but it touches ~240 rows and pushes them, so it should be a deliberate
decision rather than a side effect.

### D. Five standing type errors (low)

`tsc` has reported the same five errors for a long time
(`app/(onboarding)/_layout.tsx`, `app/_layout.tsx`, `debug.tsx`,
`animated-gradient-background.tsx`, `lib/firebase.ts`). All are benign at
runtime, all are noise that makes a new error easy to miss. Worth fixing or
suppressing one by one so the check can be trusted again.

### E. Lint warnings (low)

93 problems: 35 `react-hooks/exhaustive-deps`, 24 unused variables, 16
`require()` imports, 9 unescaped apostrophes, the rest cosmetic. The hook
warnings are the ones that can bite (stale closures); the rest is housekeeping.

### F. Taps stopped working once, in a Debug session (probably not the app)

After about forty minutes of deep links, sheets and several red JS error
overlays, the app stopped answering taps on list cards entirely, on two
different screens, until it was relaunched. It could not be reproduced in a
clean session, not by swiping sheets away and not by stacking broken deep
links. LogBox and the error overlay only exist in Debug builds, which is the
likeliest culprit, so this is noted rather than filed. Worth a second look if
it ever happens by hand on a Release build.

## What was verified as working

- **Tabs**: map, timeline, plan, tracking, settings all render and switch.
- **Timeline**: month sections, gap and overlap badges, country grouping, the
  trip sheet with its map, stats and details, the "+" menu, the photo importer.
- **Plan**: trip list with travellers' faces, trip screen with the morphing title
  chip and the travellers panel, stop sheet (dates, visa rule, stay card, tips),
  stay page (requirements, options, booking, notes) including the sheet bridge,
  documents wallet with per-person filters and faces, guides and the start-date
  sheet, new-trip sheet, add-stop flow, journey map.
- **Tracking**: year filter, hero ring, counters, visa tracker with its rules
  ("90/180 rolling window", "DTV max 180d/stay"), expired visas, tax residence
  with its disclaimer.
- **Settings**: account, passport picker, AI agent screen and connect sheet,
  cloud sync status with a working "Sync Now", location tracking, badge library
  (7 of 7), paywall.
- **Sharing**: invite sheet in the app, the public invite page, joining, and a
  member downloading a shared document.
- **Error handling**: unknown invite code, unknown guide, unknown journey and the
  three guarded screens all fail politely.
- **Backend**: 64 Cloud Function tests pass, `agentApi` refuses requests without
  a token (401), the share page 404s on a bad code, local and cloud data agree
  exactly on both accounts (240/240 trips, 2/2 journeys, 3/3 visas, 3/3 stays).

## Suggested order of work

1. Cold start and the full-collection pulls (finding A): the one thing a user
   feels on every single launch.
2. Tombstone pruning (B), which also shrinks A.
3. The one-off country name pass (C).
4. Type errors and hook warnings (D, E) when there is a quiet hour.
